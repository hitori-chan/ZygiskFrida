# AGENTS.md

Guidance for coding agents working in this repository.

## Mission

ZygiskFrida is a Zygisk/Frida/hooking framework for authorized security
research, diagnostics, reverse engineering, and community tooling. Work in this
repo should improve framework quality, reliability, compatibility,
reproducibility, and documentation.

This project is not for app-specific bypass work. Do not add changes whose main
purpose is to evade a particular app, vendor, anti-cheat, banking check, DRM
check, or security product. Keep improvements framed as general framework
engineering: safer lifecycle handling, clearer diagnostics, predictable staging,
hooking parity, tests, release quality, and documented limitations.

Preserve continuity with the original project. Keep the original author's
wording, credits, license attribution, and general ZygiskFrida direction unless
the maintainer explicitly asks to rewrite them. Do not rebrand the project away
from its upstream roots just because the implementation has moved to Rust/Cargo.

## Preferred Engineering Direction

- Keep the native runtime Rust-first. Do not reintroduce C/C++ runtime code
  unless the maintainer explicitly asks for it.
- Preserve the familiar default Frida Gadget attach flow unless the task clearly
  requires a different default.
- Prefer reliability and correctness over stealth. Surface cleanup is acceptable
  when it removes artifacts created by this module itself, but it must not become
  app/security-check bypass logic.
- Treat child gating as experimental and opt-in. Document limitations clearly,
  especially that the current PLT-hook backend covers `fork` and `vfork`, not
  `clone` or `clone3`.
- Keep config behavior strict and predictable. Invalid config should fail safely
  with useful diagnostics.
- Avoid broad refactors, build-system churn, generated artifacts, or new helper
  tooling unless they are required for the requested change.
- Keep upstream-facing project language stable. Prefer additive documentation
  when clarifying Rust/Cargo changes instead of replacing the original README
  voice or project framing.

## Safety Boundaries

Allowed work includes:

- Injection/remap correctness and parity.
- File descriptor ownership, app-data staging, sidecar config handling, and
  cleanup of files generated by ZygiskFrida.
- Diagnostics that help authorized users understand failures.
- Compatibility with Android ABIs, Magisk, KernelSU, APatch, Rust, and
  Frida releases.
- Tests, CI, reproducible builds, release packaging, and documentation.

Do not implement:

- App-specific detection bypasses or recipes.
- Stealth behavior intended to hide Frida, Zygisk, Magisk module identity,
  syscalls, `/proc` visibility, protocol traffic, ports, or security-check
  results from a particular target.
- Inline hook expansion or other invasive behavior solely to bypass security
  checks.

If a request is ambiguous, choose the reliability/documentation path and state
the boundary in the implementation notes.

## Repository Layout

- `module/src/rust`: Rust Zygisk runtime.
- `xtask`: Cargo-native build, packaging, Frida download, and flash commands.
- `template/magisk_module`: Magisk module installer template.
- `config.json.example`: default v2 runtime config.
- `docs/advanced_config.md`: main configuration reference.
- `docs/simple_config.md`: migration-oriented simple config notes.
- `.github/workflows`: CI and release automation.

## Build And Verification

Run focused checks for the area you changed. For Rust runtime work, prefer:

```shell
cargo fmt --check
cargo clippy --workspace --all-targets --all-features -- -D warnings
cargo test --workspace --locked
cargo check --package zygiskfrida --locked --target armv7-linux-androideabi
cargo check --package zygiskfrida --locked --target aarch64-linux-android
cargo check --package zygiskfrida --locked --target i686-linux-android
cargo check --package zygiskfrida --locked --target x86_64-linux-android
```

For release packaging:

```shell
cargo xtask package
```

The release zip should be written under `out/`.

Release packaging requires `curl` plus a configured Android SDK/NDK. Use
`ANDROID_HOME`, `ANDROID_SDK_ROOT`, or `sdk.dir`. If packaging fails because the
SDK/NDK is missing, report that as an environment issue instead of treating it
as a code failure.

## Code Style

- Follow the existing Rust module structure and local helper APIs.
- Use explicit plan/state objects for runtime behavior rather than passing raw
  config through late lifecycle code.
- Keep unsafe code narrow and wrapped in small helpers where practical.
- Prefer structured parsing and typed validation over ad hoc string handling.
- Keep release logs useful but avoid path-heavy diagnostics unless debug or
  verbose logging is enabled.
- Add tests for config validation, execution planning, staging, remap selection,
  loader diagnostics, and child-gating state changes when touching those areas.

## Documentation

When behavior changes, update the relevant user-facing docs:

- `README.md` for overview, build, and high-level scope.
- `docs/advanced_config.md` for config schema and runtime behavior.
- `docs/simple_config.md` for migration notes.
- `config.json.example` for default config changes.

Keep documentation honest about limitations. In particular, do not imply that
surface cleanup hides Frida, Zygisk, module identity, syscalls, `/proc`, ports,
protocol traffic, or app/security checks.

## Git Hygiene

- Do not revert user changes unless explicitly asked.
- Keep edits scoped to the requested task.
- Remove temporary artifacts before finishing.
- If CI fails remotely after local checks pass, inspect the actual GitHub Actions
  failure metadata before guessing at a fix.
